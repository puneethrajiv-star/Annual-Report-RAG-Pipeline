# Annual Report RAG Pipeline

## The problem

Annual reports are long, dense and full of financial jargon. Finding one specific number, or understanding one part of a company's business, means reading through hundreds of pages, and that has to be repeated for every company you want to compare. It is slow, and it is easy to miss things.

## The solution

This project is a retrieval-augmented generation (RAG) pipeline. It reads an annual report PDF once, splits it into searchable pieces, and stores them in a vector database. After that, you can ask a question in plain English and get an answer built from the most relevant passages and tables in the report, along with the page numbers they came from. Instead of reading the whole document, you read the answer and check it against the cited page.

It handles narrative text and financial tables separately, because tables are where most of the numbers live and where ordinary text extraction does the worst job.

Answers are generated by an LLM from retrieved text, so they can contain mistakes. Always verify important figures against the source page.

## How it works, in short

1. `extract.py` pulls out the narrative text and the tables, checks the table numbers against the original PDF, converts everything into vector embeddings, and saves them to disk.
2. `rag.py` takes your question, finds the closest matching chunks in the database, and asks Gemini to answer using only those chunks.

## File index

- `extract.py`: extracts narrative text and tables, validates table numbers, embeds chunks, and stores them in the selected collection.
- `rag.py`: loads the stored collection, retrieves relevant chunks for a question, and asks Gemini to answer from that context.
- `settings.py`: holds the PDF filename, optional page range, collection name, chunk filename and extraction thresholds.
- `requirements.txt`: the Python packages and versions needed.
- `HOW_IT_WORKS.md`: a deeper explanation of extraction, embedding, storage, retrieval and validation.
- `README.md`: this file.

## Setup and usage

1. Install the dependencies:

```bash
pip install -r requirements.txt
```

2. Download an annual report PDF and place it in the project folder.

3. Set your Gemini API key as an environment variable named `GOOGLE_API_KEY`.

Windows PowerShell:

```powershell
$env:GOOGLE_API_KEY = "your-api-key"
```

Mac and Linux:

```bash
export GOOGLE_API_KEY="your-api-key"
```

4. Open `settings.py` and set:
   - `PDF_FILE` to the PDF filename
   - `PDF_PAGES` to the page range with the main content, or `None` for automatic detection
   - `COLLECTION_NAME` to a unique collection name

5. Run extraction and indexing (needed once per report):

```bash
python extract.py
```

6. Start asking questions:

```bash
python rag.py
```

Type a question and press Enter. Type `exit` to stop.

## Tested reports

The pipeline was tested on the S&P Global FY2025 annual report and the Amazon FY2025 annual report. Retrieved answers were checked against the source documents for both.

## Example questions and answers

**Question:** What was S&P Global's 2025 revenue by segment?

**Answer:** The retrieved table reports Market Intelligence revenue of $4.902 billion, Ratings $4.549 billion, Energy $2.299 billion, Mobility $1.747 billion, Indices $1.839 billion, and consolidated revenue of $15.336 billion.

**Question:** What was Amazon's operating income for 2025?

**Answer:** Consolidated 2025 operating income was $79.975 billion. The retrieved segment table reports AWS at $45.606 billion, North America at $29.619 billion and International at $4.750 billion.

## Known limitations

- Table extraction quality varies with the PDF layout.
- Very broad or vague questions retrieve less reliably than specific ones.
- Table quality during extraction is judged by a local scoring system. An LLM check for borderline tables is a planned improvement.
- Charts and graphs are not read, because vision-based extraction is not implemented.
- When a question needs figures from several places, such as a company total and its segments, the retriever can return only some of them, so check multi-part answers.

## Design decisions

### Why 800-character chunks?

Sentence length was measured across the document and averaged about 200 characters, so an 800-character chunk holds roughly four sentences. That keeps enough context for retrieval without making matches too broad. The 100-character overlap protects ideas that fall across a chunk boundary.

### Why Camelot for tables?

The tables in these reports have no visible borders, and `pdfplumber`'s table finder missed most of them: it found about 10 tables in a document where Camelot's stream mode found 143 candidates. Stream mode uses whitespace alignment instead of borders. If a candidate scores poorly, the pipeline retries with Camelot lattice and then `pdfplumber`.

### Why check numeric fidelity?

A financial tool is only useful if its numbers can be traced to the source. The check verifies that every number in a cleaned table chunk appears in the original PDF table region. A mismatch raises an error, so a changed or invented number cannot enter the database.
